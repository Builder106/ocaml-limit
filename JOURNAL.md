## 2026-07-24 — Immediate-Or-Cancel (IOC) and Fill-Or-Kill (FOK) Institutional Order Types #feature #milestone

Expanded the OCaml 5 matching engine's order type capabilities with Immediate-Or-Cancel (IOC) and Fill-Or-Kill (FOK) institutional order types. FOK pre-scans opposing book liquidity via a non-allocating level walk to guarantee full fill or immediate rejection prior to execution; IOC matches available resting liquidity and immediately cancels any remaining unexecuted balance without placing it on the order book. Zero minor/major GC allocation on the hot path remains fully preserved (~0.0033 bytes/order, 18M-38M ops/sec, <1μs p99 latency).

Moved the dashboard to a static Vercel deploy (`ocaml-lob.vercel.app`) while the OCaml engine kept serving SSE + `POST /order`from the Oracle VM behind`ocaml-lob.duckdns.org`. The browser sniffs its own origin and points `/events`+`/order` at the Oracle host when it's running on Vercel, so the Dream server had to grow permissive CORS for the cross-origin SSE stream and the JSON POST preflight. Net effect: the part that has to be fast (the engine) stays on metal I control, and the part that just has to be reachable (static HTML/JS) sits on a CDN that won't wedge.

## 2026-05-11 — Native multi-arch via two runners, after QEMU failed once #decision #pivot

Brought back `linux/amd64`+`linux/arm64` publishing — but this time two parallel native build jobs (`ubuntu-24.04`for amd64,`ubuntu-24.04-arm`for arm64), each pushing to GHCR by digest, with a third job merging the digests into one manifest list. The first attempt (commit`153ebc1`) had run both arches through a single x86 runner with QEMU translating arm64 on the fly, and it was brutal: the OCaml compiler is single-threaded and allocation-heavy, exactly QEMU's worst case, so a ~3 min amd64 build ballooned to 30+ min and I reverted it (`6599b18`) to get a hotfix out. The native-runner split puts wallclock back at `max(amd64, arm64) ~ 3 min` with no per-arch tag clutter. Lesson banked: don't reach for QEMU to cross-compile a compiler.

## 2026-05-11 — The wedge was below our layer: WebSocket → SSE #incident #pivot #milestone

The root cause of every "container Up but URL hangs" incident in this project's life turned out to live in `gluten_lwt`'s `write_loop_step`, beneath anything application code could reach. When a WS client disconnected, gluten kept trying to flush its already-queued frames to the dead socket; each write raised, was caught by gluten's own handler, and the loop retried with no yield — one core pegged forever. We'd already tried `Lwt.choose`→`Lwt.pick`to cancel the snapshot loop on disconnect (commit`e1e883c`), wrapping fire-and-forget sends in `try%lwt … with _` (`b270665`), and a pull-from-ring rewrite so producers never queued anything async (`75cde27`) — and the spin *still* fired on a clean disconnect with zero queued frames. A `SIGUSR1` callstack dump (`32abb5f`) is what finally caught it mid-spin and pointed at gluten. The fix was to stop using WebSockets entirely: SSE over plain HTTP chunked encoding, whose close path never goes through `close_websocket`, so the spin is structurally unreachable. Demos recorded cleanly in 2.3 minutes with zero server restarts right after.

## 2026-05-11 — Added a SIGUSR1 callstack dumper because static analysis was out of moves #decision #incident

After the `Lwt.pick`and`try%lwt`fixes, the live VM still wedged: Up 5h, load 1.0, no requests served for 2h+, 307 unanswered sockets queued at the upstream. Reading the code wasn't surfacing a new culprit, so I wired a`SIGUSR1`handler that dumps the current callstack plus GC stats — trigger it from the host with`kill -USR1 $(docker inspect --format '{{.State.Pid}}' ocaml_lob)`and read the dump out of`docker logs`. Cheap enough to leave on permanently since it only fires on the signal. That dump is the single artifact that ended the multi-day hunt — it named `gluten_lwt`'s `write_loop_step`as the spinning frame. When static analysis stalls on a heisenbug, spend the hour to make the process tell you where it's parked before you`docker restart` away the evidence.

## 2026-05-10 — Tests existed but nothing ran them, so a real bug shipped for days #incident #decision

A scope gotcha in `engine.ml`shipped to production and sat there for several days: OCaml's`let … in`extends through every following semicolon until the surrounding expression closes, so in`submit`'s rest path and `fill_loop`'s iceberg-reload path the `pl_total_qty`/`pl_order_count`increments and the`was_empty`resurrection check were all silently captured *inside*the`else`branch's`let-in`body. On the`tail_idx = -1`path (every new-level submit, every resurrection) they never ran —`pl_total_qty`drifted negative and aggressive orders crossed past resurrected levels. The bench never caught it because it never reads`pl_total_qty`back out. Fix was wrapping both branches in`begin/end`to bound the`let-in`, plus six new test cases (`Sweep across levels`, `Level resurrection`) that now stand as regression sentinels. The deeper fix was a CI gate (`6f191e9`): tests existed but nothing ran them on push, so the very next commit added a `test`job that runs`dune build`+`dune runtest`*before* the image is built — that gate would have failed this regression before it ever reached the VM.

## 2026-05-10 — An 8192-slot table took down the VM after 3 hours #incident #decision

`Price_index`'s `add_aux`did an unbounded linear probe, so a full table looped forever instead of failing. On the deployed VM the demo bot's drifting mid-price accumulated unique price levels until the 8192-slot table filled, after which the next submit pegged a 1/8 OCPU at 100% and froze the Lwt scheduler — the container reported "Up" but stopped serving. Two fixes: bound the probe count so`add_aux`raises`Failure`on overflow (and`find_aux`raises`Not_found`) instead of spinning, and raise default capacity from 8192 to 65536 — ~16k distinct prices at 25% load, far more runway than the bot can realistically need, at ~512 KB per book side. Per-order allocation stayed at 0; the bench still printed VALIDATED. This was the first of several "Up but hung" incidents whose true cause (the gluten WS spin) wouldn't be found for another day.

## 2026-05-10 — Zero allocation on the hot path, six layers deep #decision #milestone

Got the matching hot path from ~16 bytes/order down to 0 by stripping every per-submit allocation in turn: pre-allocated the `Ok ()`result-wrapper constants, swapped`find_opt`for`find`+`exception Not_found`to kill`Some`boxing, lifted the`fill_loop`closure to top level, replaced`max_binding_opt`tuple boxing with an intrusive doubly-linked list of price levels, used lazy-keep-on-exhaustion + resurrection promotion instead of`Map.remove`tree-spine rebuilds, and finally replaced stdlib`Map.Make(Int)`with a custom open-addressing hashtable. Bench reports 0 bytes/order at 1M scale; throughput is 17.6 Mops/s in bench, 38 Mops/s in the clean`perf_test`, p99 0.95 μs. Same commit added `perf_test.ml`regression guards (≤0.20 bytes/order, ≥0.5 Mops/s floor, ≤100 μs p99 — all generous so they pass on under-provisioned CI runners) and`bin/diag.ml`for one-shot allocation measurement via`Gc.minor_words`. Note on measurement: the guard uses `Gc.minor_words`, not `Gc.minor_collections`, because `Gc.stat` itself allocates a 17-field record and triggers minor flushes — collection counts would measure the measurement.
